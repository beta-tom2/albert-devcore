# Albert DevCore

## Общий порядок работы для ИИ, навыков и памяти проектов

Albert DevCore помогает вести разработку с ИИ последовательно: выбрать подходящий способ работы, найти необходимый контекст, сохранить принятые решения и подтвердить результат проверками. Его основная ценность — согласованные правила, которые можно применять к нескольким проектам, сохраняя особенности каждого.

Комплект предназначен для предварительной оценки и адаптации под ваши проекты. Исходная версия кода — **16932d0713a9e4723e1d3922ec0900107edc4694**. На дату подготовки, **4 ноября 2026 года**, [PR #12](https://github.com/beta-tom2/albert-devcore/pull/12) открыт как Draft и не объединён с main. Дополнительные материалы оценки не меняют эту версию навыков или runtime.

## Три слоя комплекта

| Слой | Что входит в архив | Практическая роль |
| --- | --- | --- |
| Управляющие навыки | Три собственных пакета и вложенная инструкция восстановления | Помогают агенту выбирать подходящий процесс и специалистов |
| DevCore / ADOS | Исходники PowerShell, вспомогательные инструменты, шаблоны, документация и проверки | Создают контекст, checkpoints, очереди и проверяемые записи состояния после настройки и запуска |
| Опциональные специалисты | Каталог 33 пакетов с назначением и ссылками на авторов | Позволяет подобрать дополнительные возможности под реальный стек; сами сторонние пакеты в архив не включены |

Навык — это инструкция и связанные ресурсы, которые использует поддерживающий их клиент. Runtime — исполняемые программы. Чтобы получить конкретную возможность, нужно установить или настроить соответствующий слой. Состав ядра закреплён в [манифесте файлов](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/skills/skills-lock.json); архитектура runtime описана в [README исходной версии](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/README.md).

## 1. Albert Skill Router: подходящий процесс под конкретную задачу

Router начинает с минимального набора дополнительных навыков. Для небольшого исправления может хватить кода, локальных правил и одной проверки. Для сложной ошибки полезен последовательный поиск причины. Для существенного изменения интерфейса выбирается дизайн-маршрут; для повторяющихся проблем модульных границ — архитектурный.

Такой подход помогает ограничить объём необязательных инструкций и избежать конкурирующих рекомендаций. Решение о применении навыка зависит от задачи и ожидаемой пользы. Наличие пакета в каталоге не делает его обязательным участником каждого ответа.

Router также задаёт маршрут восстановления работы. Агент проверяет идентичность проекта, время наблюдения, исходную ревизию и актуальные источники. Принятый код, незавершённая ветка, результаты конкретного теста и готовность продукта рассматриваются раздельно. Встроенный справочник путешествует вместе с навыком: для первоначального восстановления не требуется искать документ в чужой рабочей папке.

Ссылки на специалистов обозначают зависимости маршрута. Если специалист отсутствует, агент должен назвать этот пробел и выбрать доступный способ решения, а не сообщать о применении несуществующего инструмента. Новые внешние навыки проходят отдельную оценку. Источник: [albert-skill-router](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/skills/albert-skill-router/SKILL.md).

## 2. Albert Design Director: согласованная работа над интерфейсом

Design Director помогает разделить задачи, требующие разных методов: создание визуального направления, улучшение готового экрана, исправление анимации и финальная проверка качества. При наличии соответствующих специалистов он выбирает последовательность их применения.

Например, новый экран сначала получает понятную структуру и визуальную концепцию, затем проходит проверку деталей. У существующего продукта сначала выявляются конкретные проблемы и сохраняется работающий дизайн. Анимация добавляется там, где объясняет изменение состояния, поддерживает непрерывность взаимодействия или даёт полезную обратную связь.

Правила проекта, фирменный стиль, доступность, читаемость и ограничения платформы остаются основой решений. Изменение интерфейса должно иметь проверяемый результат: скриншоты, сравнение состояний, проверку адаптивности или другой подходящий способ наблюдения. Сам Director не предоставляет браузер, эмулятор или дизайн-редактор: нужны доступные инструменты среды. Источник: [albert-design-director](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/skills/albert-design-director/SKILL.md).

## 3. Albert Architecture Review: улучшения с понятной причиной

Architecture Review организует разбор повторяющихся затруднений: слишком широких интерфейсов, скрытых зависимостей, неоднозначных терминов и участков, которые трудно проверять. Анализ начинается с конкретной области и наблюдаемых проблем.

Для каждого кандидата на улучшение предлагается объяснение: где возникает сложность, какая граница мешает работе, какой вариант уменьшит её и чем будет стоить миграция. Агент должен выделить приоритетную рекомендацию и сопоставить её с сохранением текущего решения. Это полезно, когда рефакторинг конкурирует по времени с продуктовой задачей.

Навык учитывает существующие архитектурные решения и язык предметной области. Переименование сущностей или перестройка модулей требуют обоснования в конкретном проекте. Интерактивное интервью остаётся отдельным режимом, если оно действительно нужно для выбора; ясное поручение не должно заново превращаться в длинный опрос. Источник: [albert-architecture-review](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/skills/albert-architecture-review/SKILL.md).

## Что добавляет DevCore / ADOS

Runtime позволяет реализовать часть процесса обычными программами. Он собирает ограниченный контекст по задаче, учитывает текущий Git diff, создаёт индексы и карты связей, сохраняет checkpoint и готовит передачу работы. Для повторных ошибок предусмотрены записи причин, связанных файлов, регрессионных проверок и ранее неудачных подходов.

При проверке результата инструменты сопоставляют изменения с разрешённой областью и записывают фактически выполненные проверки. Сведения связываются с состоянием репозитория: успешный старый запуск нельзя автоматически использовать как доказательство для изменившегося кода. Уровень проверки выбирается под задачу и доступные команды проекта.

Локальная очередь позволяет назначать приоритет и резервировать задачу на ограниченное время. Завершение связано с конкретным исполнением и его доказательствами. Это основа координации одного согласованного рабочего процесса; для нескольких одновременно пишущих агентов дополнительно нужны изоляция изменений и правила совместной записи.

В комплекте также есть локальные отчёты о состоянии проекта, ограниченная история метрик и подготовка расписания аудита. Конкретный scheduler требует настройки. Исходники рассчитаны прежде всего на **Windows PowerShell 5.1** и доступный Git; совместимость окружения получателя следует проверить до использования. Подробности и команды: [README runtime](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/README.md).

## Долговечная память и передача работы

Канонические требования и решения остаются в документах проекта, задачах и истории версий. Снимок памяти служит компактным указателем: какой проект наблюдался, когда, на какой ревизии, где находятся источники и какой этап был сохранён. Экспортёр использует явный список документов и хеши их закоммиченных данных.

Перед продолжением агент сверяет снимок с актуальной веткой и нужными документами. Если после наблюдения появились изменения, это становится предметом проверки. Отсутствующий результат остаётся отсутствующим; статус неопределённости не заменяется уверенностью из текста отчёта.

Для передачи следующему исполнителю нужны идентификатор задачи, исходная ревизия, ограниченная область работы, критерии приёмки и ссылки на источники. Обратный результат содержит изменения, реальные проверки, ограничения и следующее действие. Сохранение после значимого решения, проверенного этапа или блокера делает такой порядок воспроизводимым. Контракт: [Portable project state](https://github.com/beta-tom2/albert-devcore/blob/16932d0713a9e4723e1d3922ec0900107edc4694/docs/ADOS_PROJECT_STATE.md).

Это внешняя память рабочего процесса. Она сохраняет то, что было записано и доступно следующему исполнителю. Полнота зависит от качества checkpoints, маршрута чтения и соблюдения процедуры. Экспорт по умолчанию локальный; публикация, облачный доступ и обновление при выключенном компьютере требуют собственного настроенного пути.

## Как это применяется к существующим и будущим проектам

В поддерживающем локальные skills Codex пользовательская область позволяет сделать навыки доступными для разных репозиториев. Выбор по описанию происходит при подходящей задаче, а не означает обязательную загрузку всех навыков. Установка в ChatGPT workspace и установка файлов локальному клиенту имеют отдельные механизмы. Источники: [Build skills](https://learn.chatgpt.com/docs/build-skills), [Skill controls](https://learn.chatgpt.com/docs/enterprise/skills).

Для нового проекта потребуется определить его правила, стек, точку входа, проверки и разрешённые источники памяти. Глобальный Router помогает выбрать процесс, а проектная настройка связывает этот процесс с конкретным репозиторием. При создании проекта можно предусмотреть такой шаг в принятом шаблоне или процедуре развёртывания. Само появление новой папки не является подтверждением выполненной настройки.

Для существующего проекта сначала сравниваются его правила и уже работающие инструменты. Полезные элементы добавляются к ним. У каждого проекта остаётся отдельная память и граница доступа. Копирование навыка не переносит аккаунты, авторизацию коннекторов и права на сервисы другого человека. [Skill controls](https://learn.chatgpt.com/docs/enterprise/skills).

## Примеры применения

**Веб-приложение с готовым интерфейсом.** Задача — улучшить читаемость формы и мобильную компоновку. Router выбирает дизайн-маршрут; Director при наличии подходящего специалиста организует аудит существующей формы. Проверяется результат на необходимых размерах экрана. Архитектурный разбор подключается только при обнаруженной связанной проблеме.

**Мобильная загрузка данных.** Пользователь видит устаревший результат после смены фильтра. Полезен разбор причины и специалист по получению данных соответствующей платформы. Проверка должна воспроизвести последовательность запросов и подтвердить актуальность отображённого результата. Наличие общего пакета не заменяет проектных тестов.

**Продолжение после перерыва.** Новый агент получает задачу и сохранённый checkpoint, проверяет ревизию и читает только относящиеся к продолжению документы. Он восстанавливает принятые решения и незавершённые пункты. Передача может выполняться между сессиями или исполнителями при доступе к одним согласованным источникам.

**Растущий модуль.** Несколько небольших изменений постоянно затрагивают одни и те же файлы. Architecture Review помогает проверить, действительно ли причина в границах модуля, сравнить варианты и выбрать ограниченное улучшение. Результатом первого этапа может быть обоснованный план без немедленного переписывания кода.

## Подтверждённая проверка этой версии

Для подготовки выполнены **33 проверки экспорта и восстановления состояния** и **15 сценариев навыков/установщика**. Последний набор проверяет в том числе хеши файлов, установленных по manifest, включая вложенную инструкцию Router. В [PR #12](https://github.com/beta-tom2/albert-devcore/pull/12) зафиксированы условия и результаты.

Полный [Windows CI для точного commit 16932d0](https://github.com/beta-tom2/albert-devcore/actions/runs/41883039691) завершился успешно: синтаксис, вспомогательный JavaScript, smoke, восстановление состояния, очередь, пакеты навыков и чистота рабочего дерева. Эти результаты подтверждают проверенные сценарии данной ревизии. Они не являются измерением ускорения разработки или доказательством совместимости с любым новым проектом.

## Кому пакет подходит

Ожидаемая польза выше там, где несколько проектов или длительные задачи требуют регулярно восстанавливать контекст, согласовывать разные способы работы и проверять завершение. Набор также полезен для команды, которой нужны общие форматы передачи при сохранении проектных правил.

Для небольшого одноразового запроса может быть достаточно обычного диалога и одной проверки. Если уже есть надёжная система задач, памяти и автоматизации, сначала стоит сравнить пересечение функций. Начать можно с одного Router или одного доменного навыка; использование всего runtime не является обязательным условием оценки.

Критерии пилота лучше задать заранее: удалось ли восстановить задачу без повторного объяснения, сколько существенных решений потерялось, были ли необоснованные остановки, какие проверки подтвердили результат. Любые выводы о времени и расходе ресурсов должны следовать из собственных наблюдений. Проценты прироста продуктивности для этого комплекта не заявлены.

У сторонних пакетов сохраняются собственные условия.
